## Business Goal

Make key Resource Directory links discoverable from global search so users can find tools quickly from typeahead or the full search page instead of navigating manually through the Resource Directory landing page.

## Plain-English Summary

Jira calls this "Resource Library," but the LA Courts codebase and existing site copy call the feature `Resource Directory` / `Court Resources`.

Today those items were intentionally removed from global search in `LAC-227` by the shared `lacourtsearchquerycallback`. `LAC-250` is effectively the follow-up that reintroduces them in a controlled way:

- show Resource Directory items in typeahead
- expose a Resource Directory category/filter in full search
- make sure search results link to the real destination URL stored on the resource item, not just the SharePoint item path

## Acceptance Criteria

1. Resource Directory items appear in typeahead results.
2. A clearly labeled `Resource Directory` category is available in typeahead and full search.
3. Full search includes a filter/refiner for Resource Directory content.
4. Clicking a Resource Directory result opens the intended destination URL (for example, a tool link such as Time Entry -> Workday), not a broken or indirect SharePoint item URL.
5. Existing Media search behavior does not regress.

## Technical Understanding

Current behavior:

The local JS callback `window.lacourtsearchquerycallback` now scopes the `Resources` selection to `ContentType:"Court Resource"` while leaving the standard non-people searches on their normal query path.

Separately, the checked-in full search page definition is strongly document-oriented. Its query targets the site collection's Shared Documents path and common file extensions, and its refiner list is generic (`created by`, `file type`, `sites`, `categories`). There is no checked-in Resource Directory refiner or category there yet.

Latest confirmation:

The active LA Courts GenericSearchListWidget config already wires both the typeahead and full-search widget instances to the LA Courts-specific templates, `lacourtsearchquerycallback`, `LACSearchResultsCallback`, and an `extendlookin` entry named `Resources`.

The checked-in search page definition had drifted away from that setup. It was still using blank `callbackmethod` / `querycallbackmethod`, no `Resources` extend-look-in, an OOB display template, and a document-only query. That drift is now fixed in source in both the SiteCreator definition and generated build copy.

The live sandbox page still renders the stale behavior today, which proves the updated page definition has not been deployed there yet. In the rendered sandbox page, `Look in` still shows only `Document`, `Pages`, `Media`, and `People`, and the `Resources` option is absent.

Because sandbox is still stale, SharePoint indexing cannot yet be treated as the only remaining blocker for full search. Deployment of the aligned search page definition is required first, then indexing can be re-evaluated.

The dedicated Resource Directory page already proves the resource records contain the real outbound destination URL in `CourtResourceURLOWSURLH`. That matters because Jira specifically calls out link correctness such as `Time Entry -> Workday`. If global search simply shows raw SharePoint item paths, acceptance criterion 4 will fail even if the items become searchable.

Expected behavior:

Global typeahead and the full search page should include Resource Directory items under a clear label, and those results should open the actual tool/resource destination URL configured on the resource item.

## Proposed Fix

Recommendation:

Treat this as a two-part change:

1. Remove or narrow the `-ContentType:"Court Resource"` exclusion so Resource Directory items can participate in typeahead and full search.
2. Add explicit handling for Court Resource search results so they render with the correct label/category and route clicks to `CourtResourceURLOWSURLH` instead of the SharePoint record path.

Current status of that recommendation:

The local codebase now implements both parts, including aligned page-level search configuration. No additional source change is currently required for this ticket. The next gating step is deployment of the updated search page definition to sandbox, followed by retest.

For full search, Scott should also add a Resource Directory refiner/category path in the page widget configuration rather than relying only on generic categories.

Important implementation rule:

If this ticket requires changing an OOB GenericSearchListWidget template that does not already have an LA Courts-specific filename, do not modify the OOB template in place. Create a client-specific copy for LA Courts, point the widget configuration to that custom template, and keep future client work off the upgrade path.

Why this approach:

The ticket is not just "make them searchable." The dedicated Resource Directory implementation already demonstrates that these items have custom fields and a custom outbound URL. Reusing that understanding in global search is the safest way to satisfy the "proper linking" acceptance criterion.

What could make this larger than expected:

- If the typeahead category structure is controlled outside the checked-in JSON, Scott may need to update runtime widget configuration in App Manager or another site-definition source not yet found locally.
- If the default generic search result template cannot be extended cleanly, Scott may need a custom search result callback/template for Court Resource items.
- If the icon choice affects category rendering, final polish may be blocked until Theresa gets client confirmation.
